# CLAUDE.md — правила работы над проектом ZeldaArena

> Файл лежит в корне репозитория. Claude Code читает его автоматически в каждой сессии.
> Полная спецификация — `docs/SPEC.md`. Макеты — `docs/design/`. Здесь только рабочие правила.

## Проект

Киберспортивная платформа по игре Zelda: турниры, матчи с live-счётом, команды, игроки,
статистика, расписание, новости и магазин игровой периферии с корзиной и заказами.
Платная подписка даёт право создать свою команду (фича `team.create`) и расширенную статистику
(`stats.advanced`). Оплата мнимая: реквизиты карты → код на почту → подтверждение кода.

Стек: .NET 10 (LTS), ASP.NET Core MVC + Razor Pages, EF Core + PostgreSQL, MongoDB, SignalR, Clean Architecture.

Проект оценивается по 16 критериям — матрица в `docs/SPEC.md` §2.
**Любое решение, ухудшающее балл по любому критерию, недопустимо.**

## Рабочий процесс

1. **Сначала план, потом код.** Для задач сложнее однострочной правки: исследование → план → утверждение → реализация.
2. Идти строго по фазам `docs/SPEC.md` §17. Одна фаза = одна сессия = один PR. Не забегать вперёд.
3. В конце задачи: `dotnet build`, `dotnet test`, `dotnet format`, коммит, обновление `docs/PROGRESS.md`.
4. При нехватке времени резать только из «Приоритета B» (`SPEC.md` §16).
5. Противоречие в спецификации или неоднозначное бизнес-правило — **остановиться и спросить**, не решать молча.

## Архитектурные правила (нарушение = откат)

- `ZeldaArena.Domain` — только BCL. Никакого EF Core, никаких data annotations на сущностях.
- `ZeldaArena.Application` ссылается только на `Domain`; все интерфейсы к инфраструктуре объявляются здесь.
- Типы `ZeldaArena.Infrastructure` не встречаются в `Web` нигде, кроме `Program.cs`.
- Контроллеры принимают только `ISender`, `IStringLocalizer`, `ILogger`.
- Бизнес-логика — в доменных сущностях и хендлерах. Во вьюхах и контроллерах логики нет.
- Каждый сценарий = команда/запрос + хендлер + валидатор.
- У доменных сущностей нет публичных сеттеров — только методы, защищающие инварианты.
- Доменные сущности не биндятся из HTTP-запроса — только ViewModel/Command.

## Правила предметной области

- Доступ к платным функциям проверяется **только** через `IEntitlementService` / `[RequireFeature]`.
  `User.IsInRole("Premium")` для проверки доступа **запрещён** — роль Premium только для отображения.
- Коды фич — константы в `FeatureCodes`, не строковые литералы по коду.
- Счёт матча меняется только через `Match.UpdateScore()`; завершённый матч не редактируется;
  каждое изменение порождает доменное событие и уходит в SignalR.
- Цены, суммы корзины и скидки **всегда** пересчитываются на сервере.
- В `OrderItems` пишутся снапшоты цены и названия товара.
- Состав команды историчен (`RosterEntries` с `JoinedAt` / `LeftAt`).

## Безопасность

- Валидация всегда двухуровневая: клиент (DataAnnotations/unobtrusive) + сервер (FluentValidation).
- **Полный номер карты и CVV не сохраняются, не логируются и не возвращаются клиенту.**
  В БД — только `CardLast4` и `CardBrand`. Код подтверждения хранится только хешем.
- `Html.Raw` только для `RulesHtml` и `BodyHtml`, прошедших HtmlSanitizer на входе.
- Антифоржери-токен на всех изменяющих запросах, включая AJAX.
- Сырой SQL запрещён; сортировка и фильтрация — только по whitelist полей.
- Секреты — только в User Secrets и переменных окружения.
- Пароли, токены, recovery-коды, номер карты, CVV и код подтверждения не должны попадать в логи.
- Доступ к заказу, корзине, своей команде проверяется по владельцу (защита от IDOR).

## Работа с макетами

Макет — готовый HTML-шаблон. Он лежит в `docs/design/`:
`pages/*.html` — по файлу на экран; `assets/{css,js,fonts,img}` — общие ресурсы шаблона (одна копия на весь макет);
`README.md` — карта соответствия страниц шаблона страницам проекта; `design-system.md` — извлечённые токены.

**Что читать:** `docs/design/README.md`, файлы из `pages/`, авторские стили (`style.css`, `main.css`,
`custom.css` — те, что не минифицированы и не вендорские), и `design-system.md`, когда он появится.

**Что НЕ читать никогда:** минифицированные и вендорские файлы (`bootstrap*`, `jquery*`, `owl*`,
`boxicons*`, `flaticon*`, `animate*`, любые `*.min.css` и `*.min.js`), содержимое `assets/js/`,
бинарные шрифты в `assets/fonts/`. Их содержимое для вёрстки не нужно и только расходует контекст.
Часть из них закрыта правилами в `.claude/settings.json`.

**Порядок работы:**
1. В начале Фазы 5 прочитать `README.md` и все `pages/*.html`, изучить авторский css,
   составить `docs/design/design-system.md`: палитра, шрифты и шкала размеров, отступы, радиусы,
   тени, сетка, стили кнопок, карточек, бейджей, таблиц, форм.
2. Перенести токены в `wwwroot/scss/_tokens.scss` как CSS-переменные.
3. **Дальше работать по `design-system.md`, а не по исходным html.** К `pages/*.html` возвращаться
   точечно — когда верстается конкретный экран, открывать только его файл.
4. Шрифты из `assets/fonts/` и картинки из `assets/img/` копировать в `wwwroot` командами оболочки,
   не открывая их содержимое.
5. Из `assets/js/` переносить в проект **только те скрипты, которые реально используются**
   на страницах проекта. Не тащить весь набор плагинов из шаблона — это ломает требование
   по минификации и скорости загрузки.
6. Компоненты используют только переменные из `_tokens.scss`, никаких хардкод-цветов и размеров.
7. Верстать по одному экрану за раз, переиспользуя уже созданные partial-представления и ViewComponents.

## Стиль кода

- C# 14, nullable enabled, `TreatWarningsAsErrors` для `Domain` и `Application`.
- Асинхронность везде, где есть I/O; `CancellationToken` пробрасывается до конца.
- Один публичный тип на файл, имя файла = имя типа.
- Никаких магических строк: коды фич, маршруты, тексты — в константах и `.resx`.
- Комментарии объясняют «почему», а не «что».

## Git

- Conventional Commits: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`.
- Коммит = одно логическое изменение; частые мелкие коммиты лучше одного большого.
- В сообщениях коммитов не упоминать ИИ-ассистента.
- Ветка на фазу: `feature/phase-N-<описание>`, PR в `main`. Прямые коммиты в `main` не делать.

## При неопределённости

Спрашивать. Особенно по бизнес-правилам: поведение при смене тарифа; что происходит с командой
пользователя после истечения подписки (решение: команда остаётся, но редактирование блокируется);
условия отмены заказа; формат турнирной сетки. Не додумывать молча.
