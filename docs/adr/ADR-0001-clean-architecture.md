# ADR-0001: Clean Architecture из четырёх проектов с проверкой правила зависимостей тестами

- **Статус:** Принято
- **Дата:** 2026-09-06
- **Фаза:** 0

## Контекст

Задание оценивается по 16 критериям (`docs/SPEC.md` §3), и первый из них — архитектура:
пять баллов даются за Clean Architecture с разделением на отдельные проекты. Отдельно
на защите оценивается расширяемость: замена хранилища, добавление нового UI, новая платная
функция без изменения ядра (`docs/SPEC.md` §5.4).

Проблема в том, что декларация архитектуры и её соблюдение — разные вещи. Слои, разделённые
только папками внутри одного проекта, разъезжаются на второй неделе: в сущность прилетает
атрибут EF Core, в хендлер — `HttpContext`, в контроллер — `DbContext`. К моменту защиты
от заявленной архитектуры остаётся структура каталогов, и доказать соблюдение правила
нечем, кроме честного слова.

## Решение

**Четыре проекта уровня решения плюс два тестовых.** Границы слоёв — границы сборок:

```
Domain  ←  Application  ←  Infrastructure
                ↑                ↑
                └──── Web ───────┘
```

`Domain` не имеет зависимостей вообще, только BCL. `Application` ссылается только на `Domain`
и объявляет порты (`IRepository<T>`, `IEmailSender`, `IEntitlementService`, `IRealtimeNotifier`
и прочие); реализации живут в `Infrastructure`. `Web` ссылается на `Infrastructure`
единственно ради вызова `AddInfrastructure()` в `Program.cs` — это composition root, и больше
типы `Infrastructure` в слое представления не встречаются.

**Правило зависимостей проверяется автотестами, а не соглашением.** Проект
`ZeldaArena.ArchitectureTests` содержит все пять правил из `docs/SPEC.md` §5.2:

1. `Domain` не зависит от `Application`, `Infrastructure`, `Web`, EF Core, ASP.NET Core;
2. `Application` не зависит от `Infrastructure`, `Web`, EF Core, ASP.NET Core;
3. типы `ZeldaArena.Infrastructure.*` не встречаются в `Web` нигде, кроме `Program.cs`;
4. контроллеры принимают в конструктор только `ISender`, `IStringLocalizer`, `ILogger`;
5. у доменных типов нет свойств с публичным сеттером.

Правила 1 и 2 проверяются на двух уровнях: по типам (NetArchTest) и по ссылкам сборки
(`Assembly.GetReferencedAssemblies()`). Первый уровень ловит использование запрещённого типа,
второй — сам факт подключения запрещённого пакета, ещё до того как им кто-то воспользовался.

Тесты написаны в Фазе 0 целиком, до появления доменного кода. На пустых проектах проверки
по типам проходят вакуумно, поэтому в Фазе 1 к ним добавляется sentinel-тест: он утверждает,
что в `Domain` есть настоящие сущности, и страхует от ситуации, когда архитектурная проверка
молча зеленеет на пустой сборке.

Красный архитектурный тест = красный CI = незамерженный PR.

## Альтернативы

**Один проект с разделением по папкам.** Дёшево на старте и совершенно нечем защищать:
компилятор не мешает вызвать `DbContext` из вьюхи, а критерий 1 требует именно отдельных
проектов.

**Вертикальные срезы без слоёв (Vertical Slice Architecture).** Хорошо ложится на CRUD, но
задание прямо требует замену хранилища и добавление нового UI без изменения ядра
(EP-1, EP-2). Без слоя портов эти сценарии не показать. Внутри `Application` вертикальные
срезы всё же используются — папка на сценарий в `Features/`.

**Проверка руками при код-ревью.** Работает ровно до первого дедлайна.

## Последствия

Хорошо: нарушение архитектуры обнаруживается в момент внесения, а не на защите. Замена
реализации порта не задевает `Domain`, `Application` и `Web` — на этом строятся демонстрации
EP-1 (переключение хранилища новостей) и EP-6 (новый платёжный провайдер). Тестировать
`Application` можно без базы: за портами стоят подстановки.

Цена: больше файлов и церемонии — каждый сценарий это команда/запрос, хендлер и валидатор;
между HTTP-запросом и сущностью появляются ViewModel и Command; простое чтение из базы стоит
дороже, чем прямой вызов `DbContext` из контроллера. Для учебного проекта это осознанная
плата за критерий 1 и за демонстрации расширяемости.

Правило 4 (контроллер принимает только `ISender`, `IStringLocalizer`, `ILogger`) жёстче
обычной практики: оно закрывает путь «внедрю сервис прямо в контроллер», то есть пункт 1
из списка запретов `docs/SPEC.md` §20.
